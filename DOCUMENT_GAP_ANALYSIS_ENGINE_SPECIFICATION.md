## Preface

OCR reads a document. This engine decides what that reading *means* for this specific citizen's specific case — whether it satisfies a requirement, whether it's still valid, whether it agrees with everything else already known. This distinction is the entire reason this Specification exists separately from any future OCR component: extraction is perception; this is judgment, and judgment must be deterministic, auditable, and honest about what it doesn't know — the same discipline `LEGAL_INTELLIGENCE_CONSTITUTION.md` already demands of legal reasoning, applied here to documents instead of statutes.

This engine is also, concretely, the reasoning behind the single most important moment in `DEMO_DIRECTOR_BOOK.md`: the instant a citizen learns a document is missing, before they've wasted a trip finding out the hard way.

## 1. Architecture

Sits inside the Document Intelligence Subsystem (`EPIC_A_AI_CORE_ARCHITECTURE.md` Chapter 5), as the Validation Agent's concrete implementation for document-level reasoning — distinct from the OCR Agent, which only extracts fields. The engine consumes whatever the current input source provides (today: citizen self-report; later: OCR-extracted fields, without this engine's internal shape changing — see Section 10) and evaluates it against the checklist `AI_REASONING_PIPELINE_SPECIFICATION.md` Stage 07 already generated.

```
                 ┌────────────────────────────┐
                 │  Document Gap Analysis Engine │
                 │  (Validation Agent)            │
                 └──────────────┬─────────────┘
        ┌───────────────────────┼───────────────────────┐
        ▼                       ▼                       ▼
  Required Documents      Citizen-Provided Info    Citizen Profile /
  (Stage 07 checklist)    (self-report today,      Conversation History
                           OCR extraction later)    (for conflict checks)
```

## 2. Decision Flow

For every checklist item generated by Stage 07, evaluated independently before any cross-document check:

```
Checklist Item
     │
     ▼
Was it provided / confirmed?
     │
  ┌──┴──┐
  No    Yes
  │      │
  ▼      ▼
MISSING  Does it match the required document type?
         │
      ┌──┴──┐
      No    Yes
      │      │
      ▼      ▼
   INVALID  Is it still within its validity period (if applicable)?
            │
         ┌──┴──┐
         No    Yes
         │      │
         ▼      ▼
      EXPIRED  Does it conflict with another known fact or document?
               │
            ┌──┴──┐
            Yes    No
            │      │
            ▼      ▼
      CONFLICTING  COMPLETE
```

Optional items follow the same flow but never produce a status that blocks submission-readiness — their absence is recorded, not escalated, per Section 4.

## 3. Rule Evaluation

Every rule in this engine is deterministic, per Epic A's Decision Model — this engine produces only `Verified Fact` or `Escalation`, never a `Recommendation` in the sense of a soft guess:

- **Presence check** — a boolean lookup against what the citizen has confirmed or what extraction returned.
- **Type match** — the provided document's declared/extracted type equals the checklist item's required `documentId` (from `knowledge/documents/`).
- **Validity window** — where a document type has an expiry concept (e.g., `CURRENT_ID_DOCUMENT`), the extracted or stated date is compared against the current date.
- **Cross-reference check** — a field on this document (e.g., a name) is compared against the same field already on record elsewhere in the case (Memory Subsystem) or another document in the same checklist.

No rule in this list involves subjective judgment — where a real-world case doesn't cleanly resolve via these four checks (e.g., a document type ambiguous between two required items), the engine does not force a resolution; it escalates per Section 9's Human Override.

## 4. Conflict Resolution

When the Cross-Reference Check fails, this engine never silently picks a side. The resolution discipline mirrors `LEGAL_INTELLIGENCE_CONSTITUTION.md` Chapter 6's approach to conflicting legal sources, applied to conflicting facts:

- A government-database-confirmed fact (via the Memory Subsystem) outranks a freshly-provided document.
- A freshly-provided document outranks an older document already on file.
- Where two sources are of genuinely equal standing (e.g., two documents provided in the same turn), the conflict is not resolved by the engine at all — it is flagged `CONFLICTING` and routed to Section 9's human override, exactly as a tie in legal-source ranking would be.

Optional documents are never subject to conflict resolution against required ones — an optional item's absence or informal content cannot create a `CONFLICTING` status on a required item.

## 5. Confidence Model

- Each individual document's status carries its own confidence, reflecting the reliability of its input source — **Medium today**, since the only input source is unverified citizen self-report; this rises only once real OCR extraction (Section 10) provides field-level confidence of its own.
- The engine's overall gap-analysis confidence for a case is the **minimum** across every checklist item's individual confidence — identical in form to `AI_REASONING_PIPELINE_SPECIFICATION.md` Stage 09's rule, applied at the document level instead of the pipeline-stage level.
- A `CONFLICTING` or `INVALID` determination never carries High confidence, by construction — those states exist specifically because something did not cleanly resolve.

## 6. Trust Mapping

| `TRUST_CONSTITUTION.md` Ch. 4 Mechanism | How This Engine Implements It |
|---|---|
| Evidence | Every status (Missing/Invalid/Expired/Conflicting/Complete) is grounded in an actual comparison, never an assumption |
| Auditability | Every determination is logged (Section 8) |
| Human Escalation | `CONFLICTING` and ambiguous `INVALID` cases route to an officer, never resolved unilaterally |
| Consistency | The same checklist + the same provided information always yields the same status |

## 7. Failure Modes

- **False negative** (the single worst failure) — marking an actually-incomplete case `COMPLETE`, recreating the exact wasted-trip problem this entire platform exists to prevent.
- **False positive** — marking a genuinely complete document `MISSING` or `INVALID`, creating unnecessary friction and eroding the trust `DEMO_DIRECTOR_BOOK.md`'s central moment depends on.
- **Silent conflict resolution** — picking a side in a genuine conflict instead of surfacing it, exactly the failure mode Section 4 is designed to prevent structurally.
- **Blocking on an optional item** — treating an optional document's absence as if it were required, contradicting Section 2's explicit non-blocking rule for optional items.

## 8. Audit Events

One audit event per gap-analysis pass (not per document), consistent with the "one event per meaningful unit of reasoning" discipline `AI_REASONING_PIPELINE_SPECIFICATION.md` §"Audit Events" already establishes. Payload: the checklist evaluated, each item's determined status, the specific rule/comparison that produced it, the confidence, and — where applicable — the conflict details and which source outranked which. A reviewing officer or auditor reconstructs the entire determination from this one event, per `TRUST_CONSTITUTION.md` Chapter 4's Traceability requirement.

## 9. Human Override

- Any `INVALID`, `EXPIRED`, or `CONFLICTING` determination is visible to the reviewing officer with its full reasoning trail, and the officer may override it — the override itself is logged as a distinct audit event, feeding the same institutional-learning loop `LEGAL_INTELLIGENCE_CONSTITUTION.md` Chapter 9 already establishes for legal overrides.
- A citizen who disputes a `MISSING` or `INVALID` determination is not met with the AI insisting it is correct — a disputed determination is itself an escalation trigger, per `TRUST_CONSTITUTION.md`'s principle that disagreement about an AI conclusion is resolved by a human, never by the AI repeating itself more confidently.

## 10. Future OCR Integration

Today, "provided/confirmed" information comes from a citizen's simple self-report confirmation (per `MVD_IMPLEMENTATION_PLAN.md` §4's Missing Document Detector). This engine's Decision Flow (Section 2) is deliberately input-source-agnostic: when Volume 16 (OCR & Document Intelligence Specification) is authored and a real OCR Agent produces extracted fields with their own confidence, that becomes a drop-in replacement for the self-report input — **the engine's rules, decision flow, and confidence-capping logic do not change**, only the source and reliability of the "was it provided, and what does it say" input.

## 11. Future RAG Integration

Today, required-document specifications come from the static files in `knowledge/procedures/` and `knowledge/documents/`. Once Volume 15 (Legal Knowledge Base & RAG Ingestion Specification) exists, the Rule Evaluation step (Section 3) would consume dynamically retrieved, currently-verified requirements instead of static ones — again, a substitution of the requirement *source*, not a change to how this engine reasons over it.

## 12. Future Multi-Document Comparison

Today, the Cross-Reference Check (Section 3) compares one document's field against a single other source. A natural future extension generalizes this into full cross-document consistency checking across every document in a case simultaneously (e.g., name consistency across the ID card, household registration, and birth certificate all at once) — architecturally, this is the same Conflict Resolution discipline (Section 4) applied pairwise across a larger set, not a new reasoning model.

## 13. Competition Demo Mapping

This engine is the entire reasoning behind `DEMO_DIRECTOR_BOOK.md`'s 2:05–2:35 beat: the citizen marks two of three checklist items "I have this" and one "I don't have this yet"; this engine evaluates the third item's `MISSING` status and the `MissingDocumentAlert` renders — with **zero perceptible delay**, per the Demo Director Book's own §7 timing requirement, since this is Section 5's fastest-confidence, purely deterministic path with no LLM call involved.

## 14. Performance Budget

| Operation | Budget |
|---|---|
| Per-item Decision Flow evaluation (Section 2) | < 20ms |
| Full checklist gap analysis (typically 2–5 items) | < 100ms total |
| Cross-reference conflict check | < 50ms per comparison |

The entire engine must complete well under 200ms for a typical checklist — this is not a target to approach, it is the structural reason this specific interaction can be instantaneous in a live demo while Stage 11's LLM call is not.

## Known Risks

- **Confidence ceiling until OCR exists.** Every determination today rests on unverified citizen self-report, capping this engine's own confidence at Medium regardless of how deterministic its rules are — the rules are sound, but the input they operate on is not yet independently verified.
- **Cross-reference checks depend on the Memory Subsystem holding accurate prior facts.** If an earlier case or citizen record already contains an error, this engine will faithfully detect a "conflict" against that error rather than the truth — a real limitation, not a flaw in this engine's own logic.
- **No multi-document comparison yet** (Section 12) — today's engine cannot catch a name inconsistency across two documents unless one of them is directly cross-referenced against the Memory Subsystem; a real gap until that extension is built.
